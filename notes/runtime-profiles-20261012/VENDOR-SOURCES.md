## MCP conversion contract

For canonical stdio `{command, args, env, cwd}` generate:

```json
{"type":"local","command":["<command>","<arg1>"],"environment":{"NAME":"<configured-value>"},"cwd":"<configured-cwd>","enabled":true}
```

For canonical HTTP/SSE `{url, headers}` generate:

```json
{"type":"remote","url":"<configured-url>","headers":{"NAME":"<configured-value>"},"enabled":true}
```

The actual schemas accept optional timeout and OAuth settings; stdio `command` is an array, `env` becomes `environment`. `O1:packages/core/src/v1/config/mcp.ts:6`, `:44`. Avoid forwarding unsupported fields silently. Translate environment references intentionally: Pi accepts `$NAME`/`${NAME}` in compatible endpoint config, whereas OpenCode config text substitutes `{env:NAME}` (`O1:packages/opencode/src/config/variable.ts:33`). No credential values should be materialized into generated files. Canonical template rendering remains the parent's existing NAS installer responsibility.

## Role fences: native mechanisms and exact limits

1. **Pi prompt templates carry reusable prompt text, not a hard role fence.** They expand before input enters the agent (`P:packages/coding-agent/docs/prompt-templates.md:3`, `:36`). Bind each role at launch to a native `--tools` allowlist and `--exclude-tools` denylist. Merely invoking `/role` inside a broad interactive session does not change its hard fence. If role switching inside one session is later required, use the documented extension `tool_call` blocking API, with native `pi.on()` and no custom model loop (`P:packages/coding-agent/docs/extensions.md:169`).
2. **Pi MCP requires explicit filtering.** A plain builtin allowlist keeps every MCP tool registered for codemode/tool search. Include the exact permitted `mcp__...` names/patterns so the MCP allowlist is active; for a role with zero MCP grants use `--no-mcp` or deny `mcp__*`. Denials win and remain enforced when tools are activated dynamically (`P:packages/coding-agent/src/core/agent-session.ts:1537`; CLI explanation `P:packages/coding-agent/docs/cli.md:132`). For roles whose allowed Claude ToolSearch maps to native `tool_search`, consider deferred MCP exposure instead of adding arbitrary tools. Never expand an exact granted tool to a whole-server wildcard.
3. **Pi names are runtime-normalized.** `mcp__<server>__<tool>` replaces non-`[A-Za-z0-9_]` characters and can hash-truncate long/colliding names (`P:packages/coding-agent/src/extensions/mcp/tools.ts:79`). Map using canonical server/tool identity and verify native enumerated names. A simplistic replacement of one prefix is insufficient for all names.
4. **OpenCode supports native agent Markdown or the `agent` config map**, with mode, prompt, model/variant, and ordered permission rules (`O1:packages/opencode/src/config/agent.ts:13`; `O1:packages/core/src/v1/config/agent.ts:14`). Prefer `permission` over deprecated `tools`. Start with `"*":"deny"`, then grant mapped builtin permissions and exact allowed MCP names. Last matching permission rule wins (`O1:packages/opencode/src/permission/index.ts:28`). MCP names are `sanitize(server) + "_" + sanitize(tool)`, with hyphens retained (`O1:packages/opencode/src/mcp/catalog.ts:117`). Native MCP calls check that exact permission key (`O1:packages/opencode/src/session/tools.ts:408`).
5. **OpenCode MCP resource helpers share the `read` permission.** Exact `tools.{read_mcp_resource:false}` does not express the complete fence: deprecated tool booleans normalize to permissions, and visibility canonicalizes those helper names to `read` (`O1:packages/core/src/v1/config/agent.ts:68`; `O1:packages/opencode/src/permission/index.ts:204`). There is a safe native fence: `"read":{"*":"allow","mcp:*":"deny"}`. Resource listing checks `mcp:<server>:*` and resource reading checks `mcp:<server>:<uri>` (`O1:packages/opencode/src/session/tools.ts:172`, `:343`); ordinary file reads check a relative file path (`O1:packages/opencode/src/tool/read.ts:256`). Thus resource calls remain denied while filesystem reads work. A meaningful native denied-call fixture should validate this before claiming the fence tested.
6. **OpenCode edit/write/apply_patch share `edit`** (`O1:packages/opencode/src/permission/index.ts:205`). The existing isolated-builder grants edit and write together, so this representation fits that role; review roles deny edit. Native GPT model filtering may present `apply_patch` instead of edit/write (`O1:packages/opencode/src/tool/registry.ts:297`). Do not claim an individual edit-vs-write fence if a future source role separates them.
7. **Capability omissions must be explicit.** Pi has no builtin WebSearch counterpart. Drop that grant and report the reduced role capability; do not substitute unrestricted Bash or invent a new transport. OpenCode websearch exists but availability is provider/flag dependent (`O1:packages/opencode/src/tool/registry.ts:293`). Existing Claude role tools cannot be copied verbatim as runtime tool names.

## Evidence and tracker contracts

- **Pi skill activation:** `/skill:<name>` performs native file loading and expands to a `<skill name="..." location="...">` block in the user message (`P:packages/coding-agent/src/core/agent-session.ts:2148`). This is distinct from a model-issued `read` tool call of `SKILL.md`. Record the actual native activation path; catalog discovery alone is not activation evidence.
- **Pi actual calls:** JSONL `tool_execution_start/end` includes tool name, call ID, arguments, result status, duration; nested codemode calls also emit native events with parent IDs (`P:packages/coding-agent/docs/json.md:105`; `P:packages/coding-agent/docs/extensions.md:148`). A successful MCP smoke needs an actual matching MCP execution with `isError:false`, not just a model's statement or a connected catalog.
- **Pi completion/accounting:** session header includes ID/cwd; authoritative completed assistant messages include provider/model, optional concrete responseModel/responseId, usage/cost, terminal stop reason. `agent_settled` means automatic retries/recovery/queued work are finished (`P:packages/coding-agent/docs/json.md:23`, `:48`; `P:packages/coding-agent/docs/message-types.md:122`). Provider `responseId` is a response/message identifier, not automatically an HTTP request ID. Do not relabel it.
- **OpenCode actual calls:** native JSONL envelope `{type,timestamp,sessionID,...}`. `tool_use` is emitted for completed/error tool parts; inspect `part.tool`, `part.state.input`, `part.state.status`, and bounded derived result evidence. A native skill call has `part.tool == "skill"`, input name, and metadata `{name, dir}` (`O1:packages/opencode/src/cli/cmd/run.ts:720`; `O1:packages/opencode/src/tool/skill.ts:62`). MCP calls use native sanitized names, including failures.
- **OpenCode accounting:** `step_finish` contains native tokens/cost (`O1:packages/schema/src/v1/session.ts:240`). Assistant metadata includes observed modelID/providerID (`:453`), but CLI JSON stdout does not emit every assistant metadata object. Installed `opencode export --help` supports `--sanitize`; derive only necessary accounting facts in a controlled parser, without copying/publishing private sessions. The inspected v1 schema has no provider request-ID field: leave that boundary explicit and use an existing authorized transport receipt if required. SessionID, messageID, and provider request ID are different identities.
- **Tracker implementation:** consume upstream JSONL/native sanitized facts; do not build another model loop or MCP bridge. Count a skill/MCP use from observable native activation/call outcomes, not from the prompt requesting it. Keep complete private raw transcripts in their runtime-owned storage and publish only the allowed derived receipt fields.
