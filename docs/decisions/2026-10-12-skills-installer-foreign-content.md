# The skills installer does not delete content it did not write, 2026-10-12

Status: decided by the command center's ruling on #1024 (2026-10-12, 04:06Z and 04:41Z), built here as research-queue row 42 (F3), whose trigger "#1024 LANDED" fired at 06:55:24Z.

## Context

`tools/adoption/install_skills.py` runs the pinned Skills CLI (vercel-labs/skills@7407f3893ad4dceab546ac002c3ef806e4000c73) and never writes a skill folder itself. The CLI's add recreates the canonical folder from nothing (`src/installer.ts` L193-200 `cleanAndCreateDirectory`, L389-390 the write and the copy), so everything in the old folder is gone afterwards. Until #1024 the installer judged an existing folder by its `SKILL.md` alone; #1024 added the Claude Code link and the canonical-leaf link to what it protects and named this gap as not covered.

Measured with the real pinned CLI on 2026-10-12 (manifest row `gh-fix-ci`, a scratch home): after a clean install, an added `local-work.txt` in the unlocked canonical folder was deleted by the installer's run at main `83cec12ee` (`installed`, exit 0, the folder back to its 6 pinned files), and survived the run of this change (`local-modified`, exit 1, 7 files).

The first read of the pushed change (295ada5e, 2026-10-12) found two states that the first version let through, both measured with the same pinned CLI on its pinned `find-skills` source in a scratch home: a regular file named `.venv` in the unlocked canonical folder (the version excluded the name before it looked at the entry's type), and a project locked at the pin whose Claude link is missing (the repairing add returned `install` before the content check). The native add deleted the extra entry in both. The second read of the fix (9a77a96e) found a third: a lock at the pin whose `SKILL.md` was edited returned `install` before the content check (the early return tested the `SKILL.md` hash first), and the native add deleted the edit and every extra file, globally and in a project (`-a universal claude-code`); the tests repeat it with the real CLI. The fix refuses both before any add (`local-modified`, no CLI call, the file survives): `tests/test_install_skills.py::PinnedCliForeignContentTests` repeats the two measurements offline with the pinned CLI where it is installed (a local source folder, a scratch home and project, telemetry off) and fails if the classifier says anything but `local-modified` or if the native add stops deleting the entry; the fake-CLI tests cover the same states everywhere.

## Decision

1. **The folder must be what the CLI writes before an add runs over it.** Where an add is about to run over an existing canonical (or, for a Claude-Code-only copy, Claude) folder — an unlocked folder, a folder locked at the pin whose Claude link is missing or whose `SKILL.md` was edited, or a folder whose lock identifies nothing (decision 5) — the folder is the pinned tree: its git tree SHA, with the runtime-artifact directories left out, equals the manifest's `tree_sha`. Otherwise it is `local-modified`: refused unless `--force`. The same rule covers a project's canonical folder, where the locked-at-the-pin repairs are the missing Claude target and an edited `SKILL.md`; a lock that names the pin and a folder that is gone is a clean repair. A folder of `SKILL.md` alone is not exempt: a multi-file skill needs `--force` to restore its other files, and no exemption is a file type to check. A regular file, a link or a nested entry that merely bears the name of a runtime-artifact directory is content and is hashed (`git_tree_sha(..., skip_dirs_only=True)`). An entry that a git tree cannot hold, an empty directory or a special file such as a pipe, is content too: the hash would leave it out, the add deletes it (measured with the pinned CLI), so the comparison refuses it (`strict=True`, `UnrepresentedEntry`); an empty directory of a regenerated name stays regenerable.
2. **The comparison is the repository's own.** `scripts/skills_status.py` already hashes an installed folder the way git hashes a tree (`git_tree_sha`) and names the directories a skill's own tooling regenerates (`RUNTIME_ARTIFACT_DIRS`: `__pycache__`, `.venv`, `node_modules`, tool caches), and reports the comparison as `folder_tree`. The installer imports that predicate; it adds no second implementation and no network call. `check_folder_tree` leaves out only real directories of those names too (`skip_dirs_only=True`), so the status check and the installer agree on what is content; the one difference is deliberate, an empty directory or a special file, which a git tree cannot see and the installer refuses.
3. **The canonical-leaf link rule stays literal.** The first version of the rule left open whether to refuse only a link that leads to the Claude entry. It does not narrow: a link the installer did not make is content it did not write, the CLI writes a real folder at that path, and none of the 32 entries of the host's canonical skills folder is a link. `scripts/skills_status.py` now enforces the same rule (`canonical_link`, for an entry installed for Claude Code) and accepts the one layout a link on a parent folder makes, as `createSymlink` does (`src/installer.ts` L240-250), so the two required checks agree on both layouts that differed.
4. **Text items of the reads of #1024** (P3-2 the `--force` help, P3-3 the Codex-only scope of the link rule, P3-5 a missing space in a test) are fixed in the same change.
5. **A lock excuses a differing folder only by naming another revision, in the form the CLI writes one.** The third read (5ace90c1, Astra and the command center) found that the lock itself was trusted too early: a project entry without `skillPath` returned `install` before the content check, and so did one with a `computedHash` that is not 64 hex digits, one without `ref`, one that names another source and one the CLI writes for a local folder (`sourceType: local`, no `ref`, no `skillPath`); a global entry whose `skillFolderHash` is missing or empty did too. The pinned CLI makes these fields optional or does not need them whole (`src/local-lock.ts` L25-L31: `skillPath?` is "optional for backward compatibility with lock files written before this field existed" and "omitted for non-repo sources"; `ref?` is optional by its type at L19-L20; `readLocalLock` and `readSkillLock` return an empty lock for a version that is too old or a file that does not parse: `src/local-lock.ts` L83-L98, `src/skill-lock.ts` L89-L101), so an entry that lacks them says nothing about which revision wrote the folder. Measured with the real pinned CLI (offline, a local source folder, a scratch home and project; `PinnedCliForeignContentTests`) and, for the omitted `skillPath`, by Astra's reproduction with the exact pinned `find-skills` source: the classifier answered `install` and the native add deleted a local file (project, `skillPath` omitted; project, the lock as the CLI writes it for a local folder; global, an empty `skillFolderHash`). The fourth read (453ac683, Astra and the command center) found the class again in the global scope (a hash that is text but not a tree id), so the rule starts from the upstream definition, enumerated in "Lock entries" below. The rule: only an entry of the manifest's GitHub source (`sourceType` `github`, `source` the manifest's) that names another revision in the form the CLI writes one — a project `ref` that is a full commit id (40 hex digits) other than the pin's, a global `skillFolderHash` that is a git tree id (40 hex digits, matched case-insensitively as `src/update.ts` L638 does) other than the pin's tree — is an upgrade over an older pin and runs as before; every other entry (another source or type, a branch or a tag or an abbreviated id, a digest, text that is not an id, an optional field missing or malformed, no tree) is read like no lock, and so is a lock file the CLI itself reads as empty: the folder must be the pinned tree, a folder that is gone is a clean repair, and `ok` needs the whole entry (source, type, `ref`, `skillPath`, a 64-digit `computedHash`; the global tree) with the pinned `SKILL.md` and the link. A lock that is not whole is repaired once by the add, which writes it whole.

6. **A lock is read as the pinned reader reads it, in every rejection it has.** The fifth read (Astra at 23e2dcbe) reproduced two more forms that let an add run over local work, on the complete installer path and with the real pinned CLI: a lock holding `NaN`, `Infinity` or `-Infinity` (Python's `json.loads` accepts the tokens; `JSON.parse` throws, and the reader returns an empty lock), and a project lock in which another entry is local and its `source` is not text (the reader's loop throws in `isAbsolute(entry.source)`; the shape check only looked for entries that are not objects). `load_lock` now passes a hook that rejects the three tokens, and `lock_skills` reads a project lock as empty for a `null` entry and for a local entry whose `source` is not text (`src/local-lock.ts` L90-L98). One detail of the first description was wrong, and the read corrected it: the reader does not throw on an entry that is a string, a number, `true` or a list. This installer reads such a lock as empty anyway, which is stricter than the reader and stays so: a lock holding an entry the CLI cannot have written is not evidence of what it wrote. Tests: `LOCK_FILE_TABLE` gained 19 forms (`GL11`-`GL16`, `PL10`-`PL22`; 39 in all), `LOCK_FILE_STRICTER_TABLE` holds the four stricter ones, and every form runs through the classifier and through the whole installer path with the fake CLI (which now reads a lock as the pinned readers do), and two cases run the real pinned CLI.

## Measurement behind decision 2

Research row 42 asked whether the installer can prove which files of a canonical folder it wrote. On this host all 28 managed rows (`tools/adoption/install_skills.py --check-only` ok) have a folder whose git tree SHA equals the manifest's `tree_sha`: 25 exactly, 3 (`gh-address-comments`, `supply-chain-risk-auditor`, `skill-creator`) once `__pycache__` is left out (`scripts/skills_status.py --json`, `folder_trees`). The pinned vendor listing minus the CLI's copy exclusions (`src/installer.ts` L458-466) predicts the same sets file for file (checked for blob SHA-1 as well, all 28 rows), so the manifest's `tree_sha` is enough and the GitHub trees API is not needed.

## Alternatives

- **Compare against the pinned tree listing fetched from GitHub** (the oracle the project path already uses): rejected; it puts the network into `--check-only` for a global entry, and the manifest already carries the answer.
- **Add a per-file listing to the manifest:** rejected; it duplicates `tree_sha` and could drift from it.
- **Write a marker file into the installed folder:** rejected; the installer never writes a skill folder.
- **Refuse every unlocked folder:** rejected; adopting an identical hand-installed folder is a documented case ((b) of the installer), and a lost lock should not cost a `--force`.
- **Narrow the canonical-link rule:** not taken (decision 3).

## What is not covered

- An upgrade over a lock that names another revision of the manifest's GitHub source in the form the CLI writes one (a project `ref` that is a full commit id other than the pin's, a global `skillFolderHash` that is a git tree id other than the pin's): the older version's files cannot be named offline, and the lock proves the CLI wrote some earlier version there. The add runs as before. A ref that is a branch, a tag or an abbreviated id can name the pin's own commit, so it proves nothing and the folder is compared.
- A folder that is locked at the pin, linked and `ok`: no add runs, so nothing is deleted, and the folder is not judged here (`scripts/skills_status.py` reports drift).
- A pinned vendor folder that itself contains a file the CLI leaves out of a copy (`metadata.json`, `.git`, `__pypackages__`, `src/installer.ts` L458-466): its installed tree would differ from `tree_sha` and the folder would count as local content. No managed row has one today; the status check would report the same folder as `drift`.

## Overturn conditions

- A managed row whose installed folder legitimately differs from `tree_sha` (a vendor folder with CLI-excluded files): give that row an explicit expected tree, or exclude the names, in this change's predicate.
- A host layout that needs a canonical link (dotfiles-managed skills): rule on it with that host's evidence.
- The pinned CLI stops recreating the canonical folder from nothing in a later version: the protection is then stricter than the mechanism and is reviewed at the next pin.
